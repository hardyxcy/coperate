# M-003 技术方案

> 通用规则（目录、命名、锚点、校验）在 `M-005 §八`，这里不重复。

## 一、引擎与选型 {#engine v1}

待补。原生 Canvas / Cocos Creator / Laya / 白鹭 / Unity WebGL。

个人 2D 小游戏的现实建议：**玩法简单就用原生 Canvas 自己写循环**，包体最小、没有框架税、调试直观。玩法复杂或需要 3D 才上引擎。

要写清为什么不选另一个。

## 二、平台与适配 {#platform v1}

待补。微信小游戏 / 抖音 / 纯 H5。

必须写清三件事：

- 屏幕比例范围（16:9 到 20:9 都要不破）
- 安全区（刘海、底部横条、胶囊按钮）
- 竖屏还是横屏（定了就不能改）

## 三、性能预算 {#perf v1}

待补。这是硬约束，**开发前定死，开发中不放松**。

| 项 | 目标 | 红线 |
| --- | --- | --- |
| 主包体积 | | 4 MB（微信硬限制） |
| 首屏加载 | 3 秒 | |
| 帧率 | 60 fps | 30 fps |
| 内存占用 | | |

微信小游戏主包 4 MB 是死的，超了要么分包要么砍资源。这个数字应该在做第一版之前就知道。

## 四、资源管线 {#assets v1}

待补。图片压缩到什么程度、用不用图集、音频什么格式、总共多少资源。

小游戏里资源体积通常比代码大十倍，压缩策略比代码优化更值钱。

## 五、存档与数据 {#storage v1}

待补。本地存储存什么、要不要云开发存档、数据丢了怎么办。

微信本地存储上限 10 MB，且可能被清理——重要数据要想清楚能不能接受丢。
